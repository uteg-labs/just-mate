08 Architecture

Two processes, one contract

A native app and a Bun server speak one typed protocol: HTTP for accounts, the profile and onboarding; one WebSocket per phone for everything live. The contract was written first — PROTOCOL.md → @justmate/protocol → code — so mobile and backend were built in parallel against it.

Stack · mobile

Expo SDK 57, React Native 0.86, Expo Router, Reanimated 4, Gesture Handler, Bottom Sheet, expo-maps (native, hence a dev-client build — not Expo Go), expo-location, expo-sensors, expo-haptics, expo-secure-store, Better Auth Expo client, i18next.

Stack · server

Bun, Elysia (HTTP + ws), TypeBox validation, Better Auth (email + password, magic link, password reset over SMTP), Drizzle ORM with versioned migrations on PostgreSQL, OpenAI API over plain fetch (gpt-4o-mini, moderation, embeddings), i18next for server-side strings.

Stack · ML

Python with uv, PyTorch, scikit-learn, ONNX Runtime, OpenAI text-embedding-3-small. The scorer runs as an HTTP container, released to GHCR and deployed with Dokploy. A Jupyter evaluation notebook with ROC/PR curves, calibration, top-K retrieval and t-SNE of the learned space.

A match, end to end

Protocol rules that carry the product

  • The server is authoritative. Clients only request (accept, vanish) and report (position).
  • A dismiss is never forwarded. Expiry, dismiss, disconnect and a replaced search all look the same to the other side: offer_expired.
  • Bearing and bucket only, computed server-side; exact metres go only to demo sockets for tuning and are never rendered.
  • One offer or one session per user. Greedy pairing by score each tick; ties go to the shorter distance.
  • Socket close = search off. Nothing live survives a reconnect — there is nothing to reconnect to.
  • Relative times (expiresInMs), so phone clock skew never matters; unknown events are ignored, never fatal.

Built for a live stage

GPS inside an arena is unreliable, and nobody waits until Thursday on stage. A demo mode (?demo=a|b, dev builds only) feeds scripted positions through the identical pipeline: phone B converges on A over 40 s (cold → warm → hot → burning). The track is defined relative to the stage, because the compass arrow uses the phone's real magnetometer — a mismatched script would point into the audience.

Demo sockets pair only with each other; nine server-side ghosts add map density and never match. A dev time-skip makes a plan start two minutes after it is proposed. All of it is labelled in the README's real-vs-canned table.

Every 1-second tick, the server
  1. expires offers (45 s) and sessions (10 min), and puts the pair in cooldown;
  2. relays partner_position as bearing + bucket to both members of each session;
  3. pairs searchers: all pairs passing the gates, highest score first, at most one offer per user;
  4. every 2 s, sends each searcher their zones, omitting cells under k = 3.

09 Matching & AI

Not a random stranger.
Someone you'll have something to talk about.

JustMate doesn't pair you with whoever happens to be nearby. Our own AI model scores who you'd like to meet against who they are, in both directions, and scores Now matches for real accounts. Plans and the stage demo run on a transparent score we can put on a slide and defend in Q&A, which is also the model's fallback. An LLM interviews you and writes your vibe.

Hard gates — never learned, never scored

Whatever scores a pair, it only sees pairs that already passed every rule below:

  • Both searching, same mode and category, at least one shared intent (the context of the match: "this is a beer match")
  • Within walking distance: haversine ≤ the shorter of both walk settings (400 / 800 / 1200 m)
  • Age and safety: adult flag equal on both sides; Date requires adults; each side's gender preference and age range accept the other — checked both ways
  • Pair not in cooldown; neither has an open offer or session; not self; not a ghost; demo sockets only with demo sockets

The explainable score

compat = 0.7 × Jaccard(interests) + 0.3 × min(1, |shared intents|)
match  ⇔ gates pass  ∧  compat ≥ 0.45

Mode and intents gate, interests score. In Now the score is never shown — the badge and the shared intent carry the moment; a plan proposal shows it as a match percentage.

Why distance, not zone

Zones are a display unit (geohash-6, ~1.2 × 0.6 km in Kraków). Matching on "same cell" would pair people up to 1.35 km apart — more than the ~830 m a person walks in the 10-minute window — and would never pair two people 50 m apart on either side of a cell boundary.

800 m by default (a 10-minute walk): walking toward each other that is ~400 m, about 5 minutes each, leaving half the window to find each other.

Zones on the map

Each searcher gets, every 2 s, the count of compatible searchers per geohash-6 cell within 2 km. Cells with fewer than 3 are omitted, so a glow can never be followed to the only person in it.

Model: OpenAI gpt-4o-mini with strict JSON-schema output (overridable via OPENAI_MODEL). On a missing key, a timeout, an API error or output that breaks the rules, the server returns a fixed sample (source: "sample"), so the app never waits on an error path.

The learned compatibility model

An asymmetric Siamese network. Each profile is embedded twice with OpenAI text-embedding-3-small (1536-d): once as who I am (self) and once as who I'm looking for (target). A shared encoder projects both into a 128-d compatibility space; a match head scores the pair.

Shared encoder1536 → 256 → 128 · LayerNorm + ReLU · L2-normalised
Match head[ |za−zb| , za⊙zb , cos ] · 257 → 128 → 32 → 1
Directionhead(targetA, selfB) → sigmoid
Pair scoredir(A→B) + dir(B→A) — symmetric, range 0–2
Losstriplet (margin 1.0) + 0.5 · BCE
Trainingcosine LR · input noise σ 0.01 · hard negatives re-mined every 2 epochs · 80/20 split by anchor

Why two heads: raw embeddings encode general similarity, not compatibility. The triplet loss reshapes the space; the head learns the decision boundary and handles calibration.

Production path Retrain on real outcomes — mutual accept + met → 1, dismissed or vanished → 0, same again as the strongest positive; per-user vectors cached in PostgreSQL with pgvector; threshold calibrated on held-out real interactions (target FPR ≤ 5%, TPR ≥ 80%).

When a profile changes, the server scores that person against everyone; Now pairs only above the model's threshold and falls back to the explainable score while a pair has no model score.
